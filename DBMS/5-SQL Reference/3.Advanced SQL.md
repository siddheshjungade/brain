# Advanced SQL: Window Functions, Views & Procedures

Writing high-performance analytical queries and database-level code requires understanding advanced SQL structures, including Window Functions, database Views, Triggers, and Stored Procedures.

---

## 🪟 Window Functions

Window functions perform calculations across a set of table rows that are related to the current row. Unlike regular aggregate functions, window functions **do not collapse rows** into a single output row; each row retains its individual identity.

### Syntax:
```sql
SELECT column_name,
       window_function() OVER (
           PARTITION BY partition_column
           ORDER BY sort_column
       ) AS alias_name
FROM table_name;
```
- `PARTITION BY`: Divides the rows into groups (windows) to apply the function to.
- `ORDER BY`: Defines the order of rows inside each partition window.

---

### 1. Ranking Window Functions

Consider this sample dataset of employee salaries:

| Name | Dept | Salary | ROW_NUMBER | RANK | DENSE_RANK |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Alice | HR | 9000 | 1 | 1 | 1 |
| Bob | HR | 8000 | 2 | 2 | 2 |
| Charlie | HR | 8000 | 3 | 2 | 2 |
| David | HR | 7000 | 4 | 4 | 3 |

#### Difference between ranking functions:
- `ROW_NUMBER()`: Assigns a unique sequential integer to each row starting at 1. No duplicates.
- `RANK()`: Assigns ranks with gaps. Duplicate values receive the same rank, and the next rank is skipped (e.g., `1, 2, 2, 4`).
- `DENSE_RANK()`: Assigns ranks without gaps. Duplicate values receive the same rank, and the next rank is consecutive (e.g., `1, 2, 2, 3`).

```sql
SELECT name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) as row_num,
       RANK() OVER (PARTITION BY dept ORDER BY salary DESC) as rk,
       DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) as dense_rk
FROM employees;
```

---

### 2. Value/Offset Window Functions

- `LEAD(column, offset)`: Accesses data from a subsequent row in the same window (without a join).
- `LAG(column, offset)`: Accesses data from a preceding row in the same window.

```sql
-- Calculate the salary difference between the current employee and the next-highest earner
SELECT name, salary,
       LAG(salary, 1) OVER (ORDER BY salary DESC) AS higher_salary,
       salary - LAG(salary, 1) OVER (ORDER BY salary DESC) AS salary_diff
FROM employees;
```

## 👁️ Views

A view is a virtual table representing the output of a predefined SQL query. It does not store physical data in the database (with one exception).

### 1. Standard (Virtual) Views
* **How it works**: The view acts as a query shortcut. When you query a standard view, the database engine expands the view definition and runs the underlying query.
* **Pros**: Simple, does not occupy disk space, always reflects real-time data changes.
* **Cons**: Querying the view executes the underlying select query every single time, which can be slow for complex joins.
```sql
CREATE VIEW active_developer_salaries AS
SELECT name, salary
FROM employees
WHERE dept_id = 3 AND status = 'Active';
```

### 2. Materialized Views
* **How it works**: Pre-computes and physically stores the query result set on disk as a concrete table.
* **Pros**: Reading from the view is extremely fast since the work is already done.
* **Cons**: Data becomes stale when the base tables change. You must run a refresh command periodically to update the view.
```sql
CREATE MATERIALIZED VIEW sales_summary_mv AS
SELECT product_id, SUM(sales_amount) as total_sales
FROM order_items
GROUP BY product_id;

-- Refresh data in PostgreSQL
REFRESH MATERIALIZED VIEW sales_summary_mv;
```

## 📜 Procedural SQL

Procedural SQL extends declarative SQL with control flow logic (loops, if/else statements, variables).

### 1. Stored Procedures
A stored procedure is a prepared SQL code block that you save in the database.
* **Key Features**: Can accept parameters, execute complex transactions, and do **not** have to return a value. They can run DDL/DML statements.
* **Execution**: Executed using `CALL` or `EXECUTE`.

```sql
CREATE PROCEDURE update_employee_salary (
    emp_id INT,
    percentage_raise NUMERIC
)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE employees 
    SET salary = salary * (1 + percentage_raise)
    WHERE id = emp_id;
    
    COMMIT; -- Procedures can handle transaction control commits
END;
$$;

-- To call:
CALL update_employee_salary(101, 0.10);
```

### 2. User-Defined Functions (UDF)
Functions compute a value and **must return** a single value (or a table).
* **Key Restrictions**: They cannot modify the database state (no DDL/DML updates inside functions in most systems) and cannot manage transactions (no `COMMIT` or `ROLLBACK`). They can be called directly in inline SQL statements (e.g., `SELECT format_name(first, last) FROM users`).

### 3. Database Triggers
A trigger is a block of procedural code that automatically runs (fires) when a specific event occurs on a table (e.g., `BEFORE/AFTER` an `INSERT`, `UPDATE`, or `DELETE`).
* **Use Cases**: Auditing logs, enforcing complex integrity checks, auto-calculating derived fields.

```sql
-- Create audit log table
CREATE TABLE audit_logs (
    emp_id INT,
    old_salary NUMERIC,
    new_salary NUMERIC,
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Define the trigger function
CREATE OR REPLACE FUNCTION log_salary_change()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO audit_logs(emp_id, old_salary, new_salary)
        VALUES(OLD.id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Bind the trigger function to the employees table
CREATE TRIGGER salary_update_trigger
AFTER UPDATE OF salary ON employees
FOR EACH ROW
EXECUTE FUNCTION log_salary_change();
```
